# Смена сервера через расширение и HTTPS

Это отдельная явно запускаемая приёмка. Обычные тесты не используют настоящий
ZenMoney. Рабочая БД, установленный профиль Chrome и контейнер backend не нужны.

## Что проверяет сценарий

Собранный MV3 0.1.9 загружается без изменения manifest и JavaScript в новый
постоянный профиль Chromium внутри Docker/Xvfb для каждого независимого набора.
Профиль сохраняется при переключении A→B внутри набора. Popup открывается как страница
расширения, чтобы проверять его вместе с активной вкладкой банка. Банк всегда
искусственный: HTML и ответы API перехватываются до обращения к банковской сети.
Чтение коннектором, фоновые задания, storage и chrome.alarms настоящие.

У такой вкладки нет временного activeTab, которое даёт клик по значку расширения.
Поэтому стенд предварительно запрашивает разрешение только на искусственный банк
через тестовую кнопку и настоящий Chrome permissions API. Кнопка удаляется;
артефакт расширения остаётся неизменным. Открытие настоящего toolbar-popup и
банковская авторизация здесь не проверяются.

Адрес/токен серверов вводятся в штатные поля, подключение выполняет штатная
кнопка. Chrome показывает настоящее нативное окно разрешения на конкретный
сервер; Xvfb/xdotool выбирает Deny либо Allow. API разрешений не подменяется,
широкое разрешение `https://*/*` не выдаётся. Состояние проверяется через
`chrome.permissions.contains/getAll` и фактические запросы сервера.

Два независимых набора: перенос базы и новая пустая база. Для каждого:

1. Создать два собственных VND-счёта; подготовить 8 операций ZenMoney и 11
   соответствующих банковских записей. Среди них расход, приход, две одинаковые
   суммы, обе стороны одного перевода, долг. Первоначально не хватает двух записей.
2. Подключить расширение к серверу A по локальному HTTP, выбрать оба счёта и дату
   через popup. Синхронизировать: создать ровно 2 записи. Повтор: 0.
3. Остановить A и дождаться завершения worker. Для первого набора перенести
   согласованный SQLite backup в B; для второго создать B с пустой базой.
4. Подключить **тот же профиль расширения** к B по HTTPS с другим API-токеном.
   Прежние задание и дата синхронизации не должны отображаться. При перенесённой
   БД настройки счетов сохраняются; при пустой базе выбираются заново.
5. Повторно прочитать всю исходную историю. Первое чтение и повтор создают 0
   операций. Добавить одну новую банковскую запись: 1 создание; повтор: 0.
6. Независимо прочитать ZenMoney: точные UUID, исходные поля seed-операций,
   предсказанная категория, viewed=false новых записей, дневной итог и балансы
   обоих счетов. Проверить integrity/FK SQLite и отсутствие отправок старым A.

Получается 12 заданий и 6 ожидаемых новых UUID backend на два набора. У каждого
набора 12 банковских записей и 11 активных записей ZenMoney: один перевод покрывает
сразу две стороны банка. Счётчик фактических исходящих write-ID записывается до
HTTP, поэтому один лишь итоговый баланс не скрывает повторную отправку.

Отдельные проверки до подключения к B:

- отказ в разрешении Chrome: сервер не получает HTTP-запроса;
- неверный токен при доверенном TLS: 401, прежняя конфигурация сохраняется;
- доверенная цепочка с неверным именем хоста: запрос не доходит до приложения;
- недоверенный CA: запрос не доходит до приложения;
- во всех ошибочных случаях прежняя конфигурация сервера сохраняется.

## HTTPS и границы проверки

Стенд создаёт временный CA и сертификат localhost с SAN, добавляет CA только в
NSS-хранилище одноразового контейнера. Не используются `ignore_https_errors`,
`--ignore-certificate-errors`, обход SPKI или подмена fetch. Фактический HTTPS
обслуживает Uvicorn в том же контейнере; отдельный обратный прокси и публичный
сервер этим не проверяются. Сертификаты/ключи не устанавливаются на хост.

Рабочий сервер должен иметь HTTPS-адрес корня, например `https://zenimport.example.org`,
сертификат с корректным именем и полной доверенной цепочкой. В расширении вводят
этот адрес и токен **нового backend**; токен ZenMoney остаётся только на сервере.
Подпуть, query/fragment и HTTP вне localhost/127.0.0.1 запрещены. Перенаправления
не выполняются: нужен окончательный HTTPS-адрес, а не HTTP→HTTPS редирект.

Пустая база способна сопоставить существующие движения по счёту/дню/сумме,
включая переводы и долги. Она **не восстанавливает журнал прежних удалений** и
не гарантирует распознавание произвольных правок даты/суммы. Для реального переезда
рекомендуется перенос БД с остановкой старого worker. Два независимых активных
сервера на один аккаунт ZenMoney этим сценарием не разрешаются и не тестируются.
Мобильная вкладка «Новые» отдельно не проверяется: API-флаг viewed=false проверяется.

## Воспроизведение

Из корня расширения, при соседнем ZenImportBackend:

```sh
./scripts/test-server-migration.sh --fake ../ZenImportBackend
```

Этот режим использует настоящий backend/SDK с fake ZenMoney и `--network none`.
Создаётся только специальный Docker target `migration-acceptance`; обычная
совместная проверка `test-integration.sh` продолжает использовать target `integration`.

Живой режим требует отдельного явного разрешения пользователя. Не подставлять
рабочий токен. Идентичность берётся из завершённой предыдущей приёмки backend,
а токен — из проверенного тестового файла SDK:

```sh
export ZENIMPORT_LAB_IDENTITY=/absolute/private/lab/identity.json
export ZENIMPORT_TEST_TOKEN_FILE=/absolute/private/ZenMoneyAPI/.env
./scripts/test-server-migration.sh --live ../ZenImportBackend
```

Рядом с identity.json должен быть stage2-results.json. До любых записей и каждого
запуска worker проверяются сохранённый fingerprint токена, запрет рабочего токена
и фактический user полного ответа ZenMoney. Оба файла монтируются read-only;
рабочие .env/SQLite не монтируются. Существующие операции тестового аккаунта
сохраняются и независимо проверяются, новые счета имеют префикс `ZenImport CHROME`.
Автоматической очистки счетов и операций нет.

Вывод показывает только числа и boolean-результаты. Приватный каталог
`.local/browser-migration/<UUID>/` содержит intent-журнал, audit-ID, базы A/B,
профиль, сертификаты и снимки. Каталог исключён из Git и Docker build context.
Права каталога/файлов ограничены umask 077; build/output logs также приватны.

Запуск одноразовый: run-started исключает слепой повтор после прерывания.
Зафиксированный seed-intent можно только сверять чтением, автоматически отправлять
повторно нельзя. При ошибке изучить журнал, профиль и попытки; не удалять маркер и
не запускать заново поверх этого каталога. Новая явная приёмка создаёт независимые
счета с новыми UUID и не исправляет незавершённый предыдущий прогон.

Узкий режим runner `--live --resume-verified-prefix` предназначен только для
ручного восстановления стенда после завершения всех шести copied-заданий,
допуская также завершённые initial/repeat на A из набора empty, до запуска B.
Он требует прежний каталог `/state`, проверяет pinned user,
baseline, удалённые UUID/балансы, целостность БД, отсутствие незавершённой доставки
и ровно 2/1 исходящих write-ID на A/B набора copied. Если A из empty уже работал,
также проверяются полное завершение всех его заданий, ровно 2 write-ID,
удалённые записи и остатки. Повторных seed-записей, выполненных заданий и запуска
copied worker нет. Один и тот же подтверждённый префикс можно продолжить лишь раз,
с отдельным marker `resume-verified-N`; любой иной частичный прогон
останавливается для ручного разбора. Штатный shell
runner этот режим автоматически не включает.

## Основания

- [Playwright: Chrome extensions](https://playwright.dev/python/docs/chrome-extensions)
- [Chrome: permissions API](https://developer.chrome.com/docs/extensions/reference/api/permissions)
- Предыдущая HTTP-приёмка: `ZenImportBackend/docs/migration-lab.md` в соседнем проекте.

Фактические результаты этого этапа фиксируются ниже после окончания прогонов.

### Автономная приёмка, 17 октября 2026

Полный сценарий с `--network none` прошёл на Chromium 145.0.7632.0,
Linux/ARM64, Playwright 1.58.0, MV3 0.1.9: 12 заданий, 6 ожидаемых новых UUID,
0 повторных отправок. Обе базы B по HTTPS создали 0 прежних записей и по одной
новой. Проверки нативных разрешений, 401, имени хоста и недоверенного CA прошли.
Fake ZenMoney не вычисляет балансы счетов: здесь сравниваются движения, точные
UUID и поля; реальные балансы проверяются только отдельным живым прогоном.

### Живая приёмка отдельного тестового ZenMoney, 17 октября 2026

Подтверждены 12 завершённых capture/delivery-заданий: A initial/repeat,
B initial/repeat, B new/repeat для перенесённой и физически пустой БД.

| Сценарий | A: первый / повтор | B: первый / повтор | B: новая / повтор |
|---|---:|---:|---:|
| Согласованная копия БД | 2 / 0 | 0 / 0 | 1 / 0 |
| Пустая БД B | 2 / 0 | 0 / 0 | 1 / 0 |

Числа — фактические исходящие UUID новых операций, а не только итоговый net.
Всего 6 ожидаемых UUID и 0 повторных/неожиданных отправок. Для каждого набора:
12 записей банка, 11 активных UUID ZenMoney, один перевод покрывает две стороны.
Точные UUID, seed-поля, предсказанные категории, viewed=false, дневные движения,
реальные остатки обоих счетов, исходные данные тестового аккаунта и SQLite FK/
integrity проверены независимо. Данные A после переключения не отправлялись.
Все шесть проверок разрешений/HTTPS/auth завершились успешно.

Созданы только собственные тестовые сущности: четыре VND-счёта, две категории,
16 seed-операций и 6 операций через backend. Старые тестовые данные сохранены.
Рабочие ZenMoney, БД, установленное расширение и контейнер не использовались;
рабочий контейнер оставался на прежнем ID и порту 18792. Артефакт расширения
не изменялся; проверка выполнена на Chromium 145.0.7632.0 в Linux/ARM64.

В первом живом проходе шесть copied-заданий и финансовая сверка прошли, но
стенд превысил 30-секундное ожидание остановки встроенного HTTPS-сервера.
Во время продолжения обнаружено отдельное опережение polling popup: тест
мог нажать ещё отображавшуюся кнопку Stop вместо Sync. Финансовая отправка
при этом не повторялась. Стенд теперь дожидается настоящего состояния Sync,
закрывает браузер каждого независимого набора до остановки B, использует
ограниченный graceful timeout. Это изменения приёмки, а не рабочего backend.
Продолжение выполнилось по проверенному префиксу, без повторного seed или
выполненных заданий; итоговый results.json получен после остановки серверов.

Приватный живой журнал: `.local/browser-migration/c06cc618-abbd-4605-9640-6bef1d2e7f53/`.
Там сохранены исходный output.log, продолжения, audit и результаты; в Git попадает
только этот обезличенный отчёт. Нет публичного endpoint, проверки удалённого
reverse proxy, мобильного UI или гарантии произвольного сброса истории удалений.
